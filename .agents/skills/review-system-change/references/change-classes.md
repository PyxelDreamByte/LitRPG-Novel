# CAL0 Change Classes

| Class | Meaning | Normal disposition |
|---|---|---|
| Presentation clarification | Explain or expose an existing rule without changing outcomes. | Propose an update in the writable story-integration or repository-authoring layer. Never edit the locked `cal0/guide/`; a correction to pinned guidance requires a successor. |
| Parameter change | Change a calibrated value or distribution within an existing model family. | Re-run affected reference, cohort, adversarial, projection, and closure checks; issue a successor baseline. |
| Implementation correction | Make executable behavior conform to already canonical specification. | Propose a failing regression fixture, corrected successor code, rebuilt artifacts, and an appropriate patch successor outside locked `cal0/`. |
| Local rule repair | Repair a bounded rule whose intended architecture remains intact. | Propose specification, implementation, fixture, report, and manifest changes in a successor version outside locked `cal0/`. |
| Subsystem revision | Change relationships among several rules or model families. | Reopen the relevant subsystem, repeat dependent calibration/validation, and require Author approval. |
| Architecture reopening | Change governing System principles, primitive semantics, or cross-system topology. | Treat as exceptional; require explicit Author decision and a new validated baseline lineage. |

## Minimum impact questions

- Does the change create duplicated rewards, retrospective XP, or rewards from natural growth alone?
- Does it discard exact-decimal values or provenance?
- Does it reveal facts a viewpoint, interface, or observer cannot know?
- Does it bypass costs, commitments, reinforcement, assimilation, injury, or recovery?
- Does it create unearned inventory transfer, free spawning, or causal discontinuity?
- Which existing fixtures and story scenarios should fail if the change is implemented incorrectly?

Do not label an outcome a clarification if it changes any valid input's result. The review itself is read-only; implement an accepted plan only after a separate explicit implementation request.
